# Arm H hard pool: items for spot-check

24 code-analysis items (12 buggy, 12 clean) in `task/code-analysis-hard/`, manifest `task_manifest_hard.json`. Drafted Oct 25 by a Claude Code subagent; no model was called. **Difficulty is my guess** at how often Sonnet 5 gets the verdict wrong, not a measurement. Calibration decides which items stay.

**How the keys work.** `research-sprint/arm-h/keys/<id>_key_test.py` holds tests written from the docstring alone, in two groups:

- `test_basic_*` is my guess at a competent first-pass suite. These tests must pass on the item, buggy or clean. That's the evidence the bug survives ordinary testing.
- `test_key_*` is the answer-key evidence: the exposing tests for buggy items, the suspicious edge for clean ones, and, in most items, a brute-force oracle written from the docstring and run on random inputs.

For each buggy item, `reference/<id>_fixed.py` is the same file with a minimal fix applied. All its key tests must pass. That shows the exposing test is right, not just failing. `python research-sprint/arm-h/verify_items.py` checks all of this and exits 1 on any inconsistency. It also checks that the primary function has a docstring and that the agent-visible code has no comments.

**What makes a clean item produce wrong work.** The worker only says `bug` on a clean item if one of its tests encodes the wrong expectation: it misreads a rule, or follows a familiar convention the docstring overrides. So each clean item has a rule that runs against a common prior, an implementation idiom that looks wrong, or both. I expect clean items to have lower error rates than buggy ones.

## Items I'm least sure about

- **Probably too easy** (likely dropped at calibration): cah_11_month_days and cah_20_sort_dates (clean, tests just pass), cah_05_bookings, and cah_23_withdrawals (sequential-withdrawal tests can hit the bug by accident).
- **Defining property, likely tested**: cah_17_lru (hit refreshes recency) and cah_21_undo_redo (typing clears redo). The docstrings state these rules head-on, as they must for the key to be unambiguous, so careful workers will test them.
- **No key ambiguity that I can find**. Every exposing input is inside the docstring's stated domain, and every error sentence was checked against the code. Where the code raises TypeError for wrong types, the docstrings now claim ValueError only for correctly typed bad values.

## Before running H (not done here, needs edits outside these paths)

- **Display-ID collision.** `display_task_id` maps `cah_01_rate_limit` to `1-01`, the same as `ca_01_time`, and so on through `1-24`. In mixed H sequences an agent with cross-episode memory would see the same ID for different code. Renumbering the hard items `cah_51`…`cah_74` is mechanical: rename the directories, files, manifest, keys, references and this table.
- **Pool loading.** Sequence manifests resolve task ids through `DEFAULT_TASK_MANIFESTS` in `experiments/tasks.py`, which doesn't include `task/code-analysis-hard/task_manifest_hard.json` yet.
- **Thematic overlap with the existing pool.** cah_11 and cah_15 use leap-year logic like `ca_11_date`/`ca_36_date`, and cah_09 is a top-k like `ca_02_topn`. The code and spec_keys differ, so this isn't a twin leak, but worth knowing when building sequences.
